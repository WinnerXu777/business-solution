# Niche bot fixture API

Register `botsPlugin` from `apps/api/src/bots/index.ts` with an injected `resolveIdentity(request)` and `backend`. The resolver returns the verified tenant, actor and role. The plugin scopes every command to those values. `createFixtureBotsBackend()` from `apps/api/src/bots/fixture.ts` uses the repository's virtual environment or an explicit Python interpreter. It starts a local stdio worker with both definitions registered in the public `BotRegistry`. The standalone path uses fictional fixtures, fake inference and simulated adapters.

All paths below are relative to `/v1/bots`. JSON request bodies are strict. Amounts use integer CAD cents and dates use ISO 8601 calendar dates. Responses are private and have `Cache-Control: no-store`.

| Method and path                                       | Role                | Request or result                                                                                              |
| ----------------------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------- |
| `GET /definitions`                                    | Any verified role   | Definition IDs, versions, tool allowlists and budgets.                                                         |
| `GET /policies`                                       | Admin               | Current `version`, `procurement` and `collections`.                                                            |
| `PUT /policies`                                       | Admin               | Full replacement with `expectedVersion`, `procurement` and `collections`. A stale version returns 409.         |
| `POST /procurement/requests`                          | Operator or admin   | `{source, sourceId, text, route?}`. Source is `chat` or `email`, and route is `native` (default) or `byo`.     |
| `POST /procurement/requests/:id/approve`              | Designated approver | `{approvalId}` for a locally drafted fixture request. Returns a local PO.                                      |
| `GET /procurement/exceptions`                         | Any verified role   | Current intake, purchasing and match exceptions.                                                               |
| `POST /procurement/orders/:id/receipts`               | Operator or admin   | `{id, lines: [{skuId, quantity}]}`. Returns cumulative receipt quantities and partial/complete status.         |
| `GET /procurement/orders/:id/matches`                 | Any verified role   | Three-way-match results for the specified PO.                                                                  |
| `POST /procurement/orders/:id/matches`                | Operator or admin   | `{id, vendorId, currency: "CAD", lines: [{skuId, quantity, unitCostCents}]}`.                                  |
| `POST /collections/dunning`                           | Operator or admin   | `{invoiceId}`. Returns a held or escalated decision, or a pending contact with an exact preview.               |
| `POST /collections/replies`                           | Operator or admin   | `{invoiceId, replyId, text, route?}`. Records an opt-out, dispute, explicit promise, or staff escalation.      |
| `GET /collections/accounts/:id/timeline`              | Any verified role   | Account events in ingestion order, including outreach attempts, escalations and decisions.                     |
| `GET /collections/invoices/:id/promise`               | Any verified role   | The latest captured promise and its follow-up status.                                                          |
| `GET /collections/invoices/:id/payment-plan`          | Any verified role   | The current pending or approved plan and installment schedule.                                                 |
| `POST /collections/payment-plans`                     | Operator or admin   | `{invoiceId, installments, firstDueOn, intervalDays}`. Returns a pending staff approval or a staff escalation. |
| `POST /collections/invoices/:id/payment-plan/approve` | Designated approver | `{approvalId}` using the pending plan ID. Records an approved schedule.                                        |
| `GET /runs/:id`                                       | Run creator         | Runtime state, pending approval and result.                                                                    |
| `POST /runs/:id/resume`                               | Designated approver | `{approvalId}` from the verified runtime approval. Returns the settled or interrupted run.                     |

The four run-creating routes require an `Idempotency-Key` header. They return HTTP 202 with `{id, botId, version, status, result, pending}`. An exact retry returns the current run. A different command or input with the same scoped key returns 409. Governed denials appear inside the run. Authentication errors use 401, forbidden roles use 403, missing and foreign records use 404, malformed inputs use 400, and an unavailable worker uses 503. The standalone fake gateway accepts `actor-operator` for normal fixture tool calls and `actor-approver` for approval. Use `actor-admin` for policy settings.

## Walkthrough

1. Submit `{"source":"chat","sourceId":"demo-1","text":"Draft pr-001"}` as the operator. The run cites the requisition, SKU, supplier quote and cost centre. It recommends `vendor-002` for 60 units of `sku-001` at 420 cents each and interrupts for `actor-approver`.
2. Resume as that approver. Add a partial receipt of 25 units. An invoice for 26 units enters the exceptions queue. Add the remaining 35 units and retry the same invoice document. Within tolerance it matches and clears its exception. A changed invoice under the same invoice ID is rejected.
3. Submit an email-style intake such as `Please buy 10 units of sku-001 by 2026-11-26, cost centre stock-toronto.` The extractor requires explicit SKU IDs, quantities, date and cost centre for new requests. It uses a model proposal only if those fields agree with the text. A one-day deadline selects the expedited vendor. Fresh fixture drafts use the request approval route. The sandbox simulates higher-tier routing by designating `actor-finance` or `actor-executive`.
4. Evaluate dunning for `inv-001`. Approve its exact simulated preview as `actor-approver`. To exercise the contact-window and cadence branches, use the Python service with an injected clock and contact check. A reply of `We will pay $300.50 on 2026-11-26.` records a promise and pauses reminders until after that date. A reply of `STOP` suppresses all later outreach to that account, including any already prepared run. `inv-003` is disputed and `inv-004` is suppressed in the shared fixture.
5. Submit a three-installment plan for `inv-001` with `firstDueOn` set to `2026-12-01` and `intervalDays` set to 14. Inspect the pending plan, approve separately and verify the hold on ordinary reminders. The bot records a proposal and an internal approval. It performs no payment transaction.

## Defaults and scope

- Procurement reserves fixture budget for accepted drafts. Manager review applies through CAD 500.00, finance through CAD 2,500.00, and executive review above that. Operator authority is CAD 1,000.00 and the stock cost centre starts with CAD 5,000.00. Vendor selection filters by deadline and minimum reliability, then ranks the total adjusted cost including lead days, reliability and a preferred-supplier credit. Open fixture drafts with the same cost centre and SKU quantities are duplicates across channels.
- Three-way match uses cumulative receipts and previously matched invoice quantities. It blocks quantity overruns and allows an absolute 200 basis-point unit price difference by default. The simulation covers merchandise lines in CAD. Taxes, freight, credits, budget reservation release and exception resolution beyond retrying a stored document need the shared record lifecycle.
- Collections starts with email only, a 7/5/4/3 day minimum cadence by bucket, a rolling three-attempt cap per account and staff escalation at 91 days. Email, SMS and voice share that cadence. The fixture rechecks policy, suppression, disputes, channel permission, time window, balance and cadence at approval. Unknown delivery holds later outreach.
