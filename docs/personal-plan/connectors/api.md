# Connector API

Register `connectorsPlugin` from `apps/api/src/connectors/index.ts` with a shared `ConnectorLifecycle`, `ConnectorSync`, `WebhookIngestor`, and a verified identity resolver. The resolver enforces each operation's permission and derives tenant and actor from the session. Browser OAuth callbacks require the session of the actor who started authorization. The plugin can be exercised independently with Fastify injection.

| Method and path                                                         | Permission          | Request and result                                                                                                                                                                           |
| ----------------------------------------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /connectors`                                                       | `connectors:read`   | Returns the catalog of versioned manifests.                                                                                                                                                  |
| `POST /connectors/install`                                              | `connectors:manage` | Send `connectorId`, expected provider `accountId`, and optional `mode` (`primary` or `shadow`). Returns 201 with the binding.                                                                |
| `POST /connectors/:connectionId/oauth/start`                            | `connectors:manage` | Returns `authorizeUrl` with PKCE S256 and a ten-minute state.                                                                                                                                |
| `GET /connectors/oauth/callback`                                        | `connectors:manage` | Pass the provider's `state` and `code`. The state resolves the binding. Exchanges the code, verifies the account, and attempts activation.                                                   |
| `POST /connectors/:connectionId/api-key`                                | `connectors:manage` | Send `key`. Stores the key, verifies the account, and attempts activation.                                                                                                                   |
| `POST /connectors/:connectionId/{verify,activate,pause,refresh,revoke}` | `connectors:manage` | Runs one lifecycle operation. Use `verify` or `activate` to resume after a recoverable verification or activation failure. `refresh` applies to OAuth.                                       |
| `GET /connectors/:connectionId/status`                                  | `connectors:read`   | Returns the binding, verification time, and the timestamp and checkpoint of the last committed snapshot or poll page.                                                                        |
| `POST /connectors/:connectionId/sync`                                   | `connectors:sync`   | Send `{"mode":"snapshot"}` for a full import, or `{"mode":"poll","maxPages":10}` for incremental sync. A poll returns the committed checkpoint, completed page count, and continuation flag. |
| `GET /connectors/:connectionId/reconciliation`                          | `connectors:read`   | Returns the latest sync report or `null` before the first sync. Reports include missing, added, changed, and conflicting record keys.                                                        |
| `POST /connectors/:connectionId/reconciliation/shadow`                  | `connectors:read`   | Send `candidateId` and `mappings`. Each mapping has a `primary` and a `candidate`, both with a `recordClass` and `externalId`. Returns the comparison report.                                |
| `GET /connectors/:connectionId/dead-letters`                            | `connectors:read`   | Lists safe metadata for failed webhook hydration.                                                                                                                                            |
| `POST /connectors/:connectionId/webhooks`                               | Per-binding HMAC    | Accepts the signed JSON delivery and returns 202 with `accepted`, `duplicate`, `out_of_order`, or `dead_lettered`.                                                                           |

Errors have an `error` code. Common responses include 401 for invalid credentials or signature, 403 for missing permission or an unexpected account, 404 for missing or foreign bindings, 409 for lifecycle conflicts, 422 for unsupported operations, 429 for rate limits, and 502 for an unavailable provider. Rate-limit errors include `Retry-After` when available.

## Fixture webhook format

Send `application/json` with `x-connector-timestamp` as Unix seconds and `x-connector-signature` as the hex HMAC-SHA256 of the timestamp, a period, and the exact request bytes. The default tolerance is five minutes in either direction. The body contains `schemaVersion` (1), `eventId`, `accountId`, `recordClass`, `externalId`, a nonnegative per-entity integer `sequence`, and UTC `occurredAt`. The binding and account must match. Event IDs are deduplicated per connection and account. Older sequences are skipped and gaps are allowed because hydration reads current provider state. Polling is the backstop for failed or missed deliveries.

## Sync and writes

- The record ID is derived from tenant, connection, provider account, record class and external ID. Each observation carries source version, provider update time and observation time. A full snapshot marks previously seen, absent records as missing while retaining their last observed data. Provider tombstones mark explicit deletions. A contested latest revision stays in the report until a newer valid observation resolves it.
- Snapshot checkpoints must describe the same provider view as the snapshot. Poll cursors are opaque and scoped to the binding. Providers are responsible for overlap and deletion semantics. Each validated page commits its records, report, and checkpoint together in process. A later failed page resumes from the last committed checkpoint.
- Shadow bindings have separate caches and reject writes. Compare the primary and candidate using explicitly reviewed mappings, freeze writes for the capability, and reconcile outstanding effects before a cutover. Unmapped active identities appear as missing or added. Activation of a replacement primary requires releasing the previous owner.
- `ConnectorWrites` is a service seam for the governed worker. It requires a caller-supplied authorizer for the exact intent. Use the stable effect ID for upstream idempotency and to reconcile the attempt; an ambiguous outcome freezes new writes to that capability until reconciliation. A resolved same-key retry returns the previous outcome. Any subsequent recovery write needs a fresh, separately authorized intent.

## Fixture and integration boundaries

The catalog fixtures cover QuickBooks Online-shaped customers, invoices, and payments, and HubSpot-shaped companies, contacts, and deals. The accounting fixture is read-only. The CRM fixture supports an optimistic update for tests. Both use an in-process HTTP client and synthetic accounts. `createFixtureConnectors().consent(authorizeUrl)` simulates user consent locally.

Bindings, cached records, checkpoints, webhook receipts and dead letters, and write outcomes are process-local in this implementation. OAuth state and credentials have storage interfaces. Connect the vault through `CredentialStore` and provide an atomic OAuth state store and per-binding webhook secrets before enabling a deployed route. Keep OAuth callback queries, API-key bodies, headers, state, and provider credentials out of proxy and application request logs. Use the verified session, a fixed redirect registration, and the same OAuth state store on the callback path. Apply platform CSRF checks on management requests authenticated by a browser session.

The partner MCP adapter uses operator-pinned servers, tool names, protocol versions and scopes through an injected transport. The caller verifier returns actor and tenant after audience, membership, and scope checks. Upstream calls use a separate provider grant, checked for partner audience, account, and scopes. Wire transport, issuer verification and partner endpoint configuration at the platform boundary.
