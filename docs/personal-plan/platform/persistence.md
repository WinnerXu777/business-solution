# Platform persistence

The platform stores service state and redacted audit entries through one injected repository interface. The host can use `platformPostgres(pool)` with PostgreSQL or `MemoryPlatformPersistence` for fixture runs. Both implementations run the same repository contract tests. The PostgreSQL tests inject a fake query executor.

## Tables and collections

[Migration 004](../../../infra/migrations/004_platform_state.sql) creates `platform.tenant_state`. Its primary key is `(tenant_id, collection, id)` and its payload is JSONB. Migration 007 adds an optimistic version and backfills existing webhook deliveries and notification read receipts into separate collections. Existing plan revisions, bindings, invoice snapshots, credentials, and audit entries keep their stored representations.

| Service                 | Collections and record keys                                                                                                                                                                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Directory               | `tenants` and `workspaces` use tenant IDs. `users`, `memberships`, and `membership_epochs` use actor IDs. `roles` uses role IDs. `invites` and `oidc_subjects` use SHA-256 digests. `tenant_exports` uses export request IDs.                                            |
| Auth                    | `refresh_families` and `session_revocations` use family IDs. `refresh_tokens` and `enrollments` use token digests.                                                                                                                                                       |
| Settings and secrets    | `entitlements` uses module IDs, `bindings` uses capability IDs, `connections` uses connection IDs, and `credentials` uses credential references. `credential_keys` holds the wrapped current tenant key.                                                                 |
| Billing                 | `billing_plans` holds the subscription revisions. `billing_usage` uses outcome or provider-attempt keys. `billing_invoices` and `billing_credits` use invoice IDs for idempotent close and credit.                                                                       |
| Compliance              | `consents` uses consent IDs, `suppressions` uses channel and destination digests, and `contact_attempts` uses attempt IDs. `privacy_requests` and `retention_holds` use record IDs. `retention_policies` uses data classes with fixture defaults for missing rows.       |
| Eventing                | `platform_events` uses stable producer event IDs, `webhooks` uses endpoint IDs, `webhook_deliveries` uses delivery IDs, and `notifications` uses the event and user pair. Each dead delivery has one replay slot.                                                        |
| Reporting and approvals | `audit` uses append-only audit IDs. `approval_previews` holds sanitized PO preview metadata keyed by governance approval ID. `gateway_requests` holds digests for the branch's fixture-only retry bridge. Governance owns approval decisions and its own reporting rows. |

A fixture tenant is initialized once on first directory access. Membership and tenant epochs invalidate sessions after role changes, removal, re-enrollment, or suspension. Refresh and enrollment tokens encode a tenant routing hint followed by a random secret. The digest of the entire token must match a record within that tenant. Rotate a refresh token and update its family in one transaction. Keep a stable signing key across hosts for access tokens to survive process restarts. In-progress OIDC authorization redirects still use process-local state and require callback affinity. Platform-wide suppressions use the reserved scope `@platform-suppressions`. A trusted path opens that scope explicitly. Tenant repositories never inherit it.

## Transactions and row-level security

Each platform operation checks out a client, starts a transaction, sets `SET LOCAL ROLE platform_app`, and sets the tenant with parameterized `set_config('app.tenant_id', $1, true)`, the equivalent of `SET LOCAL app.tenant_id`. The executor scopes standalone reads and writes too. An operation within an existing same-tenant transaction uses the same client. Nested work joins the outer transaction and cross-tenant nesting fails. State and platform audit use that transaction, including consent and invoice events, webhook claims and settlements, and session changes. The original migration's trigger guards audit rows from updates and deletion.

RLS is enabled and forced on the physical platform table. The `USING` and `WITH CHECK` predicates require the row's tenant to match the local setting. Missing or empty settings expose zero rows and reject inserts. The application role is a non-owner with schema usage, table row DML, and sequence usage. It has no `BYPASSRLS` or `TRUNCATE`. RLS is defense in depth against a missing tenant predicate. The application still authenticates and authorizes requests before it chooses a tenant, since a database caller with the application role can set the scope.

Platform business transactions serialize per tenant with a PostgreSQL advisory transaction lock. Repository updates and deletes also compare the version they read. Inserts and replay slots are unique in PostgreSQL. A stale version or existing key becomes a repository conflict and is returned as HTTP 409 by the platform routes. A webhook worker locks only the specific delivery with `SELECT ... FOR UPDATE SKIP LOCKED`, persists the attempt and lease before calling the injected transport, and settles only the same attempt. A lost or expired lease can lead to redelivery, so receivers should deduplicate using `x-platform-delivery`.

## Lane A bootstrap

1. Move `007_platform_tenant_isolation.sql` into `infra/migrations/` after 006. Run the existing migration runner as the schema owner with permission to create the role. Keep the unnumbered [RLS test script](migrations/test_platform_tenant_isolation.sql) outside the automatic migration sequence.
2. Give the platform pool a restricted login and grant it membership with `GRANT platform_app TO <platform_login>;`. Create a separate `pg.Pool` from `BS_PLATFORM_DATABASE_URL` for the same database as the governance pool. The governance connection may be held while its hooks use platform repositories. Close the platform pool in the host's `onClose` hook. Supply a stable vault master key and, when mounting OIDC login, a stable session signing key.
3. Keep the existing governed gateway options and pass that gateway directly to `createPlatformServices`. Set `persistence: platformPool ? platformPostgres(platformPool) : undefined` and retain `fixtureUsageBridge: false`. Keep the governed `moduleOverride`, `resolveLlmBinding`, and billing callbacks. The factory's governance adapter calls `listApprovals`, `signApproval`, and `rejectApproval`; PO approval still uses the governed PO tool. Platform reporting reads `reportingSnapshot(tenantId).audit` and `listUsage(tenantId)` on demand.
4. Remove `connectPlatformGateway` and the platform reporting snapshot hook from `apps/api/src/app.ts`. Register `app.register(platformRoutes, { services, verifyIdentity })` directly. Pass `governed` as `gateway` in the shared governance transport so its export and dead-letter readers remain available. In automation, call `services.gateway.call` and `services.gateway.signApproval` where platform event fanout is desired, and retain the approval lookup through `governed.listApprovals`. In `authorizeRuntime`, use `const role = (await services.directory.resolve(scope))?.role`. The fixture verifier and session verifier are asynchronous. Use the same `services.directory` to construct `PlatformAuth` if the host enables OIDC.
5. To dispatch fixture webhooks, inject the fake `webhookTransport` when constructing services and call `await services.events.deliverDue(tenantId)` for each trusted, active tenant on the host's worker tick. Use configured fixture tenant IDs for the Milestone 1 walkthrough. The scoped executor expects one tenant per call.

Run `psql "$BS_PLATFORM_DATABASE_URL" -f docs/personal-plan/platform/migrations/test_platform_tenant_isolation.sql` against the disposable migrated database. The script checks unmapped sessions, cross-tenant reads, inserts, updates and deletes, tenant reassignment, same-tenant invite uniqueness, and transaction-local cleanup. It rolls back its synthetic rows.

Governance decisions and the platform outbox are separate transactions. The facade uses stable event IDs when publishing after a governed result. The governance store remains the source of truth if the process exits between those commits. External privacy record deletion also uses its existing idempotent source contract and commits separately from platform state.
