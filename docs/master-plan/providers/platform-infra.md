# Platform infrastructure providers

**Live research snapshot — 2026-11-24 (Toronto).** The pricing and licence columns record public vendor documentation, source licences or commercial terms checked for this snapshot. USD unless a source labels another currency. Prices are list-rate examples, before applicable taxes, overages, infrastructure and add-ons. A quote or unverified field represents a gap in public evidence for the exact product or deployment. The **SMB fit** column and the architecture below are recommendations.

**Residency scope.** “CA self-host” means the application can be deployed in Canada on infrastructure we control. “CA region” applies only to the named service and data plane. Before promising Canada-only handling, confirm processing and storage of payloads, metadata, credentials, backups, logs and traces, plus support access, subprocessors and disaster recovery. PIPEDA allows cross-border processing subject to accountability and safeguards. Québec’s private-sector privacy law requires a privacy impact assessment before communicating personal information outside Québec, including transfers elsewhere in Canada, and a written agreement reflecting the assessment when the transfer proceeds. Customer contracts and sector rules can impose further limits. [OPC cross-border guidance](https://www.priv.gc.ca/en/privacy-topics/airports-and-borders/gl_dab_090127/) · [Québec private-sector act, s. 17](https://www.legisquebec.gouv.qc.ca/en/document/cs/P-39.1)

## MCP gateways, registries, authorization and hosting

For protected HTTP MCP, implement and test the **2026-07-28** revision and negotiate supported versions with older servers. The spec uses OAuth 2.1, with MCP as a protected resource, resource metadata (RFC 9728), discoverable authorization-server metadata, resource indicators/audience validation and PKCE. Client ID Metadata Documents are recommended; dynamic client registration is optional and deprecated in that revision. Distinguish tenant authorization to invoke a tool from the downstream SaaS grant. Validate issuer, audience, expiry and scopes, and keep credentials scoped to tenant, user and connector. Never pass through the incoming MCP token as a downstream credential. [Release](https://blog.modelcontextprotocol.io/posts/2026-07-28/) · [Authorization specification](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/index.mdx) · [Security considerations](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/security-considerations.mdx)

## Provider abstraction per tenant and capability

Use a **versioned capability registry** scoped to tenant and regional cell. Resolve each capability to a platform default or an approved tenant override when a workflow version is published or a run is admitted, depending on the binding. Persist the resolved snapshot for replay and audit. Keep stable platform IDs for workflow definitions, runs, usage events, invoice references and connector links. Store external IDs in adapter-owned mapping tables. Allow configuration overrides only for explicitly tiered and supported adapters.

~~~ts
type Capability = "workflow" | "bot" | "connector" | "identity" |
                  "policy" | "meter" | "billing" | "telemetry";
type Context = {
  tenantId: TenantId;
  actorId: ActorId;
  cell: CellId;
  requestId: string;
};
type Binding = {
  capability: Capability;
  adapterId: string;
  version: number;
  externalAccountRef?: string;
  credentialRef?: SecretRef;
  processingProfileId: string;
  features: ReadonlySet<string>;
};
type Execution = {
  context: Context;
  binding: Binding;
  operationId: string; // Stable across retries
};

interface WorkflowPort {
  start(exec: Execution, definition: GraphVersion, input: DataRef): Promise<RunRef>;
  signal(exec: Execution, run: RunRef, signal: RunSignal): Promise<void>;
  status(exec: Execution, run: RunRef): Promise<RunStatus>;
}
interface ConnectorPort {
  invoke(exec: Execution, tool: ToolVersion, input: DataRef): Promise<ToolResult>;
}
interface PolicyPort {
  decide(exec: Execution, request: PolicyInput): Promise<PolicyDecision>;
}
interface MeterPort {
  record(exec: Execution, event: UsageEvent): Promise<UsageReceipt>;
}
interface BillingPort {
  applySubscriptionChange(exec: Execution, change: SubscriptionChange): Promise<BillingRef>;
  pushUsage(exec: Execution, event: UsageEvent): Promise<BillingReceipt>;
}
~~~

- **Routing and isolation.** Fetch the authenticated tenant/cell server-side. Validate adapter region, credential ownership, required features, data classes and egress authorization at binding time and execution. Use immutable binding versions and secret references; fetch short-lived credentials in-region. Treat hosted iPaaS, MCP and model tools as egress destinations. Default-deny incompatible, unavailable or unapproved bindings. Audit config changes and use an explicit, policy-approved recovery route if applicable.
- **Stable contracts.** Keep workflow support for timers, signals, cancellation and approvals explicit in manifests. Keep connector tool schemas and scopes versioned. Map identity federation to internal principals and keep it outside workflow replay. Keep observability behind OTLP exporters and keep authoritative audit storage controlled by the platform. A tenant policy adapter can apply extra restrictions; platform safety, entitlement and data boundary checks always run.
- **Reliable handoffs.** Normalize retryable, permanent, unsupported and unknown-outcome errors. Write usage to an internal ledger plus outbox with unique tenant/event IDs. Deduplicate billing webhooks by verified provider/account/event ID, tie them to internal records and reconcile invoices. For external writes, use stable idempotency keys where supported and reconcile unknown outcomes before retrying. For tools without idempotency, isolate and explicitly handle ambiguous results.
- **Switching providers.** Validate residency, licence, scopes, schema parity and limits in sandbox. Switch only new workflow runs and drain old runs on their original engine, or migrate explicitly using application checkpoints. Reauthorize connector credentials where required. Stage identity switches using verified account linking and migrate billing at a clean cycle boundary with ledger replay checks and protection against duplicate invoicing. Keep old mappings until rollback and retention windows close. Cloud changes move a whole cell through an explicit data migration. Customer UI continues to use the same graph format and internal IDs.
